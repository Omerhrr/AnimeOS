# AnimeOS - AI-Native Animation Production Platform

> **DSH decides · Tools execute · Engine builds · State remembers**

AnimeOS is an AI-native production studio for animated and illustrated storytelling. It natively supports **donghua**, **anime**, **manhua/manhwa (comics)** and adjacent formats through one unified, stateful production pipeline - designed so an AI director (DSH) drives the studio through tools, not ad-hoc chat.

## Core thesis

```
DSH decides → tools execute → engine builds → render → DSH evaluates → revise → approve
```

Every step writes to a persistent production universe: projects, seasons, episodes, scenes, shots, characters (with episode-resolved states), relationships, assets, terminology and continuity events. Nothing lives only in a chat log.

**Stack:** Next.js 16 · TypeScript · Prisma/SQLite · TanStack Query · zustand · Tailwind · shadcn/ui · Three.js.

Per the replaceability principle, the render engine is a **pluggable driver** chain: headless Blender workers when a `blender` binary exists, the built-in MOTION engine (ffmpeg) otherwise, a wall-clock simulator as the last resort - the production state machine, queue and DSH evaluation loop are identical.

### Render engines

- **Headless Blender (auto-detected).** If a `blender` binary is on the machine (or `ANIMEOS_BLENDER_BIN` points at one), each render job spawns a fresh worker: `blender -b -P bridges/blender/animeos_bridge.py -- --worker --job <file>`. The worker builds a stand-in 3D scene (rocky terrace, moon/rim/energy lights), drives a camera rig through the shot's movement grammar frame by frame, applies the AnimeOS scene parameters, renders with Cycles CPU and encodes h264 (system ffmpeg, or Blender's own FFMPEG writer). Shots carrying a pose program get a **skeletal stand-in figure** (jointed humanoid with the emissive blade in hand) whose joints interpolate between the start/end poses with eased timing - lunges, casts, walk cycles with stride swing and root bob - and the rig follows the subject's travel so the body stays framed. One 3D worker at a time; overflow jobs fall to the MOTION engine.
- **MOTION engine (built-in).** A deterministic camera program (per-movement zoom/pan/tilt profiles x shot-type framing x lens character x lighting grade x fog/lightning/energy) is animated over the shot's key art with ffmpeg zoompan - or over a procedural gradient plate when no art exists - and encoded at the project's fps. Pose pairs play here as a blocking approximation: the program notes them and lands an impact beat at the end pose.
- **img2vid provider (real, built in).** Pose-carrying hero shots route to the built-in **z.ai interpolation model** by default: the shot's key art (inlined as a data URL - no public host needed) plus a pose/camera program (the pose gloss, the movement and framing, an identity lock on the art's character) go to the async video-generation API; the finished clip downloads back into `public/renders/` and plays in the same queue. The provider chain is: an attached host wins (`ANIMEOS_IMG2VID_HOST` speaking the tiny jobs protocol), then the z.ai model, then the built-in engines; set `ANIMEOS_IMG2VID=off` to keep the slot empty. A provider lost mid-job degrades to the MOTION engine transparently.
- **Workstation attach.** Run the bridge server inside any Blender (GUI or headless) and point `ANIMEOS_BLENDER_HOST` at it: jobs go over HTTP and the finished clip returns as base64.

```bash
# inside any Blender ≥ 3.x (GUI or headless):
blender -b -P bridges/blender/animeos_bridge.py -- --port 8100
# then point the studio at it and restart the dev server:
ANIMEOS_BLENDER_HOST=127.0.0.1:8100 bun run dev
```

The add-on exposes `GET /status`, `GET /progress`, `POST /render`, `POST /ping` on `127.0.0.1`. Every engine maps the tunable scene parameters (fog, lightning, energy, rim light, camera distance) onto its own equivalents, honors the shot grammar (ESTABLISHING→24mm wide … EXTREME_CLOSEUP→100mm), streams per-frame progress into the same queue UI, and lands an mp4 in `public/renders/`. If an attached bridge drops mid-job the driver chain takes over transparently.

```bash
bun install
cp .env.example .env      # DATABASE_URL=file:./db/custom.db
bun x prisma db push

```

The database auto-seeds on first request with the **Immortal Path** demo production: a donghua universe with character development states, a six-shot Scene 12 breakdown, a seeded continuity conflict (Jade Sword destroyed in Ep 29) and terminology entries.

### Try the loop

1. Open **Render Queue**, trigger a render on any shot - the **Engine driver** card shows whether headless Blender workers or the built-in MOTION engine is driving; the job badge shows `BLENDER`, `IMG2VID` or `MOTION`. Watch progress stream per frame, then **play the finished clip right on the job card** - a dolly-in on a closeup dollies, a pan pans. Give the shot a **pose program** first (panel inspector > Motion poses, or DSH `set_shot_poses`) and the clip shows the character performing: the Blender stand-in lunges, casts or walks between the start and end poses. Or skip the authoring: hit the panel inspector's **Use state poses** and the featured character's episode-active state lands its preset (a furious state performs STANCE → LUNGE).
2. Same view, pick an episode in **Episode cut** and hit *Export cut (mp4)*: the episode's clips concatenate in story order, the stems synthesize server-side (real TTS takes included) and video + audio mux into one downloadable cut with its manifest.
3. Watch the evaluation come back `NEEDS_REVISION` with bounded parameter fixes → **Apply fixes** auto-queues attempt 2.
4. Open **DSH Director** and talk to the studio: *"For scene 12 shot 3: author the dialogue, generate a model sheet for any new character, then paint the panel in manhua style"* - the 34-tool trace shows the director doing it itself. Ask it to *"shift to a cold moonlit silver-blue palette"* and it retunes the production's style direction itself.
5. Open **Characters** - hit ✦ on a character to generate their **model sheet**; the stored anchor then steers every panel they appear in (cards show an `ANCHOR` badge once locked).
6. Open **Comic Mode** and flip the same episode between manhua / webtoon / manga layouts. Bubbles (speech / thought / SFX) place themselves around the art - mirrored for manga RTL - **Print / PDF** exports pages with chrome hidden, and in webtoon format **Export slices** downloads a ZIP of 800px platform-ready strips whose audio stems mix real TTS voice takes into the score.
7. In **Comic Mode**, open **Motion sound** on a motion panel: auto-score the timeline, hit **Render voices** to give every dialogue cue a real TTS take performed by the speaker's cast artist in the speaker's current character state (or pick a voice, speed and an explicit excited / injured delivery per cue, plus a directorial note), and preview - exported stems use the same takes. Author **line-level delivery** in the dialogue editor (the ✎ on any panel) to play one shot's lines in mixed registers; the motion-sound board shows which line direction outranks the standing one.
8. Open **Artists** to run **voice casting**: give each roster artist a TTS voice, then bind characters to the artist who speaks for them. **Audition** any voice first - the board renders a throwaway sample (your line, or the character's own first line, in a chosen register) without saving a take - or pick a development state under a character and hear exactly how that state performs (variant voice + speed/pitch hints). Every proposed read lands in the state's **audition history** (replayable, removable), and **any two recorded reads chain back to back**: pick sides A and B, hit *compare A · B*, and hear them one after the other. Select several characters for an **ensemble try** and DSH or the board renders an A/B row per speaker with a sequence play. Ask DSH to do the same with `cast_voice_actor`, and to set standing deliveries scene-wide with `direct_voice_takes`.
9. After a state beat or a line edit, open **Direction diff** in the Comic Mode toolbar: every take is compared against today's direction and **Re-render affected** touches only the stale ones (fresh takes are never re-rendered).
10. Open **LoRA** and hit **Train all** to batch-fine-tune every idle adapter from the approved panels (each run shows a live loss curve), or **Train** a single one; then open **Workload** and hit **Distribute pool (affinity-first)** to route unassigned panels to the artist whose style affinity is highest for each panel's adapter.
11. Back in **Render Queue**, use **Batch render**: tick two episodes, hit *Queue N renders*, and watch the queue fill, DSH inspect each preview (throttled per poll), and the stats row track active / review / approved.

## Status

The full thesis runs end-to-end: DSH directs dialogue, panel art, model sheets, style direction, scene staffing, voice casting and state-aware voice direction through 34 production tools; renders are real animated clips - a headless Blender worker pool or the built-in MOTION engine animates every shot's camera grammar into an h264 cut that plays straight on the queue card, and episode exports mux those clips with server-synthesized stems into one distributable mp4; Comic Mode produces AI-illustrated, dialogue-authored, casting-consistent pages in all three native formats, directs voices line by line inside a shot, auditions cast choices and whole character states before committing them, remembers every proposed read per state with a replayable A/B-chainable history, exports webtoon platform slices whose audio stems carry cast-artist, character-state-shaped TTS voice takes over the synthesized score, diffs every episode's direction and re-renders only the takes that moved, measures the whole season's state arcs on a cross-episode ruler with one lane per speaker, paints beats from reusable arc templates (saved per production or in the studio library, versioned, usage-counted, diffable across scopes), lands ensemble beats on several speakers in one batch with same-turn auditions and playable arc chips in the reply itself, batch-trains style adapters from approved panels, and routes the panel pool affinity-first while ranking per-artist style affinity, and the queue swallows whole episodes in one batch.

## Roadmap - what is not achieved yet, and how we will get there

The plan's destination is an AI-native studio that takes a story from prose to published, animated episodes with zero manual coordination. The thesis loop is closed, but these parts of the vision are still open:

1. **Performance-grade character motion.** Characters move inside the frame: shots carry start/end pose chips (13-pose vocabulary), every development state carries a **pose preset** (auto-resolved from the label, steerable per state, landable on shots in one click), the Blender worker articulates a skeletal stand-in between the poses, the **built-in z.ai img2vid provider** turns the key art into real interpolated video (host attachable, kill-switchable), and the MOTION engine plays an impact-beat approximation. What is still missing: facial performance and finger-level articulation, physics-accurate interaction with props and cloth, and learned interpolation quality on par with the best closed video models. Next: upgrade the stand-in rig (faces, hands, secondary motion) and add a per-provider latency/cost readout on the queue card.
2. **Continuity checking that sees the universe, not just the sheet.** The art layer joined the continuity engine: a deterministic scan flags stale art (panel predates the episode-active state or the current model-sheet anchor) and missing anchors, and a **VLM deep check** compares a hero panel against the character's canonical model sheet, filing ART_DRIFT / ART_VERIFIED events automatically. What is still missing: comparing against the universe FACTS (props, injuries, destroyed artefacts) rather than only the character sheet, a confidence score per verdict, and auto re-paint of drifted panels. Next: feed the universe facts into the vision prompt, threshold verdicts into the re-render queue the way direction staleness works today.
3. **DSH across turns and days.** The director plans within one 4-round turn; a multi-episode breakdown still needs a human in the loop between messages. Next: persist DSH plans as first-class, resumable objects (plan → steps → done), add scheduled agent runs (nightly batch breakdowns, render-queue supervision) and a plan review UI where the creator approves the next chapter before it executes.
4. **Voice scale and character voices.** TTS is a fixed catalog of voices with rate-limit ceilings (the E2E suite backs off on 429s), and voices are cast, not cloned. Next: a provider abstraction with retry/backoff plus render caching keyed on voice + text + delivery + speed/pitch, and a cloning-provider slot so a character's voice is trained once and performed everywhere.
5. **Evaluation that measures consistency.** Render evaluation is LLM-graded on composition; nothing scores whether the character actually looks like the anchor. Next: embedding-based similarity scoring per panel against the stored anchor, thresholded into the re-render queue the same way direction staleness is today.
6. **A studio with more than one person in it.** Multi-artist routing exists, but there is one login, no roles, and no review threads. Next: auth with per-role views (director / artist / voice actor), comment threads anchored to panels and takes, and an approval gate that feeds the same render pipeline.
7. **Distribution beyond the file.** Webtoon slices, print PDFs and episode cuts download locally; nothing schedules or publishes. Next: a release calendar with per-platform presets and direct upload integrations, built on the existing slice pre-flight and cut manifest.

Each item lands the same way the last twelve iterations did: one thin, testable slice at a time, every step verified against the production database and the running studio.
