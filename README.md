# AnimeOS - AI-Native Animation Production Platform

> **DSH decides · Tools execute · Engine builds · State remembers**

AnimeOS is an AI-native production studio for animated and illustrated storytelling. It natively supports **donghua**, **anime**, **manhua/manhwa (comics)** and adjacent formats through one unified, stateful production pipeline - designed so an AI director (DSH) drives the studio through tools, not ad-hoc chat.

## Core thesis

```
DSH decides → tools execute → engine builds → render → DSH evaluates → revise → approve
```

Every step writes to a persistent production universe: projects, seasons, episodes, scenes, shots, characters (with episode-resolved states), relationships, assets, terminology and continuity events. Nothing lives only in a chat log.

│   ├── views/          # studio views (dashboard, dsh-console, comic, …)
│   ├── preview/        # three.js cinematic preview
│   └── studio/         # app shell (zustand + TanStack Query)
└── lib/
    ├── dsh/            # tools, prompts, orchestrator, evaluator
    ├── ai/             # art service: panel art + character model sheets
    ├── bridge/         # MOTION engine (ffmpeg camera grammar) + Blender bridge
    ├── blender/        # NATIVE runtime (provisioning + resident server + exec) + asset library
    ├── engine/         # render pipeline (Blender ⇄ MOTION ⇄ simulator drivers)

**Stack:** Next.js 16 · TypeScript · Prisma/SQLite · TanStack Query · zustand · Tailwind · shadcn/ui · Three.js.

Per the replaceability principle, the render engine is a **pluggable driver** chain: headless Blender workers when a `blender` binary exists, the built-in MOTION engine (ffmpeg) otherwise, a wall-clock simulator as the last resort - the production state machine, queue and DSH evaluation loop are identical.

### Render engines

- **Headless Blender (auto-detected).** If a `blender` binary is on the machine (or `ANIMEOS_BLENDER_BIN` points at one), each render job spawns a fresh worker: `blender -b -P bridges/blender/animeos_bridge.py -- --worker --job <file>`. Since v4.0 the worker renders the DESIGNED pass: AnimeOS compiles the production's design text (model-sheet anchors, appearance notes, wardrobe/weapon states, environment briefs) into design DNA (`src/lib/animation/design.ts`) and sends it with every job, so the worker builds the DESIGNED character (stylized smooth figure, layered robes with sleeves, cuffs, sash and skirt panels, hairstyle per DNA - topknot / ponytail / braid / long / short, per-DNA weapon - sword / staff / spear - with the character's energy color, high collar, glowing stylized eyes) on a DESIGNED set (terrain per environment - terrace / peak / forest / gorge / temple - plus features: two moons, pagoda silhouette, bronze bell, wind banners, pillar stubs, bamboo, sea of clouds, lanterns, waterfall and stream, with a time-of-day sky and key light; a second detected character blocks across the set). A prop-scale camera table frames the 0.9m figure properly (chest/face-height targets, 1.9x distances). Without DNA the worker falls back to the v3.3 stand-in figure and set. It builds the set and drives a camera rig through the shot's movement grammar frame by frame, applies the AnimeOS scene parameters, renders with Cycles CPU and encodes h264 (system ffmpeg, or Blender's own FFMPEG writer). Shots carrying a pose program get an **articulated stand-in figure** whose joints interpolate between the start/end poses with eased timing - lunges, casts, walk cycles with stride swing and root bob - and the rig follows the subject's travel so the body stays framed. And since iteration 74 the body can PERFORM instead of slide: a keyed choreography program (design_choreography / set_shot_choreography - built-ins The Combo, The Draw Storm, The Rising Fang) replaces the two-pose interpolation with keys - anticipation earns the strike, the strike explodes, the hold sells the read, the follow-through settles - while a REAL impact light flares and the camera takes a decaying punch on the strike frame and the striking limb smears up to 1.35x on the fastest frames (the keys own the body; the lens, the cloth, the flesh and the physics still answer it). The v3.2 rig adds a **face and hands**: emissive eyes that squint and blink on a deterministic schedule, brows that knit angry or lift surprised, a mouth that opens with effort, and on each arm a palm, four fingers and a thumb that curl into grips, spread to channel energy or extend an index to point - every pose carries a 7-channel face/hand row eased between the endpoints exactly like the joints, and tight shot types aim the camera at the head so closeups frame the performance. The v3.3 rig makes the face **speak**: a shot with SPEECH dialogue and a tight framing arrives with a millisecond viseme program and the mouth performs the lines frame by frame - vowels open, m/b/p press shut, "ee" spreads, "oo" purses, and the pose's effort mouth stays as the floor. The program is **audio-driven over the real TTS take**: the take's WAV is analyzed frame by frame (RMS energy opens the mouth, zero-crossing rate separates voiced vowels from wide fricative hisses, silence closes), so the lips match the audio the viewer hears; the v3.4 program adds the **neural viseme pass**: an LLM plans the dialogue's phoneme-level mouth shapes (a 15-entry vocabulary - round oo, wide ee, lips-shut stops - weights clamped, cached per line set) and the plan's identity is CONFORMED onto the audio envelope, which keeps ownership of openness and timing, so consonants land where the words put them; without a take the plan performs the line itself, and a refused model degrades to the audio-only then text pass without blocking the render. Since iteration 75 the workers form a POOL (`ANIMEOS_RENDER_WORKERS`, default 2, clamped 1..4, read live): two Cycles workers render CONCURRENTLY, and when the pool is full a PREVIEW overflows to the MOTION engine while a FINAL PARKS in a priority wait queue (FINAL over PREVIEW, older first, an honest 3D-WAIT stage line) until a slot frees - the tick pumps the queue within one poll, and a waiter lost to a server restart fails honestly instead of hanging.
- **MOTION engine (built-in).** A deterministic camera program (per-movement zoom/pan/tilt profiles x shot-type framing x lens character x lighting grade x fog/lightning/energy) is animated over the shot's key art with ffmpeg zoompan - or over a procedural gradient plate when no art exists - and encoded at the project's fps. Pose pairs play here as a blocking approximation: the program notes them and lands an impact beat at the end pose. Speaking closeups get a blocking speech beat per spoken line (a soft shimmer over each line's window) so the cut still reads as "someone is talking here".
- **img2vid previz slot (opt-in, default off).** Demoted: the studio's output is designed, not generated, so the interpolation model is previz and benchmark only. When explicitly enabled (`ANIMEOS_IMG2VID=on|zai|previz`) or a host is attached, pose-carrying hero shots route to it: the shot's key art (inlined as a data URL) plus a pose/camera program go to the async video-generation API; on a speaking closeup the prompt also carries the lines as explicit speech direction; the finished animatic downloads back into `public/renders/` and plays in the same queue behind a PREVIZ chip. An attached host wins (`ANIMEOS_IMG2VID_HOST` speaking the tiny jobs protocol); unset flag and no host means the slot is invisible and the designed engines (Blender, MOTION) take every job. A provider lost mid-job degrades to the MOTION engine transparently (and rebuilds the speech program so the takeover keeps the lip-sync).
- **Native Blender runtime + asset library (v4.1).** The studio owns its Blender: `src/lib/blender/runtime.ts` detects the binary, auto-provisions the pinned release (Blender 5.2.2 LTS from download.blender.org since iteration 72 - the proven 4.3.2 stays as a fallback candidate) when a workspace reset wipes it, starts a RESIDENT headless bridge on :8101 that it health-probes and restarts with backoff (the per-job spawn path stays as fallback), and exposes an exec sandbox (`blender_exec`) where the DSH designer runs real bpy passes. The design-time library (`src/lib/blender/assets.ts` + `bridges/blender/asset_builder.py`): one design DNA in, one versioned .blend + a lit 512px Cycles preview out (`assets/blender/`, previews served from `/assets-blender/`), a `BlenderAsset` row per character/environment carrying version, build log, DNA audit and an honest vision identity score vs the canonical sheet. READY assets ride every render payload; the worker appends the .blend and resolves the SAME v3.x/v4.0 rig contract by base object name, so poses, lip-sync and camera math are untouched - a missing file falls back to the procedural DNA builders honestly, and the worker state reports `figureSource` / `setSource` so every job's asset decision is auditable.
- **Workstation attach.** Run the bridge server inside any Blender (GUI or headless) and point `ANIMEOS_BLENDER_HOST` at it: jobs go over HTTP and the finished clip returns as base64.

```bash
# inside any Blender ≥ 3.x (GUI or headless):
blender -b -P bridges/blender/animeos_bridge.py -- --port 8100
# then point the studio at it and restart the dev server:
ANIMEOS_BLENDER_HOST=127.0.0.1:8100 bun run dev
```

The add-on exposes `GET /status`, `GET /progress`, `POST /render`, `POST /ping` on `127.0.0.1`. Every engine maps the tunable scene parameters (fog, lightning, energy, rim light, camera distance) onto its own equivalents, honors the shot grammar (ESTABLISHING→24mm wide … EXTREME_CLOSEUP→100mm), streams per-frame progress into the same queue UI, and lands an mp4 in `public/renders/`. If an attached bridge drops mid-job the driver chain takes over transparently.
